# 문제 해결과 개선 과제

## Grafana만 HTTP 503

- 증상: 웹사이트와 Argo CD는 열리지만 Grafana만 503 응답.
- 확인: Grafana 파드 상태·이벤트, 노드의 남은 자원, PVC/EBS와 노드의 AZ 비교.
- 원인: EBS를 연결할 수 있는 AZ와 파드의 자원·배치 조건이 함께 맞아야 했습니다. 다른 AZ의 노드 증가만으로 실행 조건이 해결되지 않았습니다.
- 조치: AZ별 노드 그룹과 모니터링 배치·자원 조건을 조정하고 기존 PVC를 유지해 재배치한 뒤 접속을 확인했습니다.
- 배운 점: ALB 503을 접속 계층 문제로만 보지 않고 실제 대상 파드와 저장 공간까지 확인합니다.

## 새 저장소 OIDC 인증 거부

Actions의 `AssumeRoleWithWebIdentity` 실패에서 실제 OIDC subject와 IAM 신뢰 조건을 비교했습니다. 저장소 이름뿐 아니라 계정·저장소의 숫자 ID를 포함하는 식별값도 일치해야 하는 환경이었습니다. 프로젝트 역할 조건을 맞추고 이미지 게시를 재확인했습니다.

이 복사본은 새 저장소의 OIDC 설정을 GitHub에서 읽어 확인한 subject를 코드에 적용했습니다. AWS 역할 생성·인증 시험은 이번 작업에서 실행하지 않았습니다. 원본의 OIDC Provider나 실제 AWS 역할을 변경한 것은 아닙니다.

## 삭제 자동화의 필수 입력 누락

`alert_email` 전달 누락으로 Terraform 실행이 멈췄습니다. 삭제할 때도 구성을 읽으므로 필요한 입력값을 전달해야 했습니다. 전달 로직을 수정하고 회귀 검사 후 중단된 단계부터 재개했습니다. 과거 해당 수정의 112개 검사 통과 기록과 이번 전체 로컬 검사 결과는 서로 다른 실행입니다.

## 배포 시연의 상세 링크 오류

V2에서 `id`·`productId` 불일치를 재현했습니다. 새 이미지·Pod Ready·홈페이지 200만으로 이 사용자 기능 실패를 검출하지 못했습니다. V1 이미지로 복구한 뒤 파라미터를 일치시키고 상품 카드에서 상세 로더까지 실행하는 회귀 검사를 추가했습니다. 최종 코드는 수정한 V3입니다.

## 남은 개선 과제

- 전체 AZ 장애 시 모든 서비스의 가용성을 통합 검증하지 않았습니다. 단일 파드 서비스와 DB 전환 중 영향이 남습니다.
- 메일 발송 후 DynamoDB 기록 실패 구간의 중복 가능성이 남습니다.
- DPAPI 기반 복구를 다른 PC·사용자까지 확장하려면 별도 비밀 정보 복구 설계가 필요합니다.
- 원본 환경의 이미지와 실행 이력은 새 저장소·새 ECR로 자동 이전되지 않습니다.
- 이 저장소 설정값으로 AWS 재배포·권한·롤백을 다시 확인해야 합니다. 이번 작업은 코드·문서와 로컬 검사까지입니다.
