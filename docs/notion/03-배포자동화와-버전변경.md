# 배포 자동화와 버전 변경

## 배포 흐름

```text
소스 변경 → 관련 서비스 검사·Docker 빌드 → ECR 게시
→ 이미지 변경 배포 PR → 다른 팀원 승인·병합
→ Argo CD가 main의 Kustomize 반영 → EKS 파드 교체
→ CodeBuild에서 배포 버전·상태·HTTPS·API 검사
```

Actions는 OIDC로 AWS에 인증합니다. CodeBuild는 VPC 내부에서 검사하며 앱 배포 자체는 Argo CD가 담당합니다. `deploy-check.yml`에는 배포 선언 변경 시 트리거가 있지만 저장소 변수 `ENABLE_DEPLOY_CHECKS=true`가 필요합니다. 발표에 사용한 실행에서는 검증 workflow를 수동 실행한 기록도 있으므로 자동 트리거 코드와 당시 실행 방식을 구분합니다.

## 서비스별 빌드

`scripts/ci/changed_services.py`가 변경 경로를 보고 member·product·ordering·apigateway·frontend 중 대상을 선택합니다. 공통 CI·테스트 변경은 전체 빌드할 수 있습니다. `full_build`는 최초 환경 준비와 복구용입니다. 테스트가 실패하면 정상 이미지 게시 단계로 진행하지 않습니다.

## 승인과 추적

- `build-push.yml`: 검사·테스트·이미지 빌드·ECR 게시·배포 PR 제안
- `review-policy.yml`: 배포를 시작한 사람과 다른 권한 있는 팀원의 현재 커밋 승인 확인
- 브랜치 보호: `required-ci`, `release-approval`, 최소 동료 승인 등 실제 병합 조건 설정
- `deploy/release.json`: 서비스별 소스 SHA, digest, 변경 서비스, workflow run 기록
- `app/msa/kustomization.yaml`: Argo CD가 적용할 이미지 이름·태그·digest

워크플로와 정책 파일을 복사해도 새 저장소의 브랜치 보호·팀원 권한이 자동 설정되지는 않습니다. 이번 복사에서 협업 초대·보호 설정·게시 활성화는 실행하지 않았습니다.

## V1·V2·롤백·V3

| 단계 | 변경 | 확인 |
| --- | --- | --- |
| 초기 테스트 | 전달받은 웹소스의 실행 환경 준비 | 접속과 주요 기능 동작 |
| V1 | 자동화 환경의 정상 기준 버전 | 같은 상품·상세·기본 기능 |
| V2 | 디자인 변경과 격리 환경 상세 링크 오류 재현 | 새 화면, 파드 교체, 상품 상세 실패 |
| V1 롤백 | 검증한 이전 이미지로 복구 PR | 이미지·상세 기능·기존 재고 유지 |
| V3 | 링크 파라미터 수정, 회귀 검사 추가 | 디자인 유지·상세 기능 복구·검사 PASS |

V1은 초기 디자인을 참고한 시연 버전이며 관리자·장바구니·주문 등은 통합된 현재 구현을 포함합니다. 초기 개발자 소스를 전혀 수정하지 않고 그대로 복구한 것이라고 설명하지 않습니다. V2 오류는 `id`와 `productId` 불일치를 의도적으로 재현한 시험입니다. [원본 시연 기록](https://github.com/yonginfra/Final_Project/blob/main/docs/20-original-storefront-demo.md)

## 롤백 범위

이전 정상 release를 검토해 이미지 변경 PR을 만들고 승인 후 반영합니다. `rollback_release.py`는 해당 release의 여러 서비스 이미지를 함께 다룰 수 있으므로 변경 대상과 digest를 확인합니다. 프런트엔드 복구 시연에서 DB나 Terraform을 되돌린 것은 아닙니다. Git에 이미지 정보가 있어도 ECR 삭제 후 이미지가 남아 있다는 뜻은 아닙니다.

현재 복사본의 배포 선언과 runId는 원본 이력입니다. 새 저장소에서 전체 이미지를 게시하고 새 배포 PR을 생성해야 새 저장소의 승인 검사와 연결됩니다. [환경 이전 안내](https://github.com/yonginfra/Final_Project/blob/main/docs/final/07-migration.md)
